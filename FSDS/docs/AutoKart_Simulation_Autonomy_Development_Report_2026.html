AUTOKART  |  EXECUTIVE SUMMARY

Executive Summary

Engineering status as of 28 September 2026

The project has progressed from an FSDS checkout and manual ROS bridge bring-up into a substantial autonomy research platform. The current tree contains ten ROS 2 packages, 31 launch/operation scripts, 78 relevant source/configuration files, and approximately 9,093 lines of C++/Python source. It supports configurable sensor contracts, manual control, RGB-D visualization, VIO/VSLAM baselines, repeatable benchmark manifests, LiDAR cone planning, SLAM-based teach-and-repeat, and behavior-cloning data collection/inference infrastructure.

Confirmed progress
The canonical simulator and ROS settings are repository-local. LiDAR, RGB, metric depth, IMU and depth point-cloud topics have been observed. The standalone packaged simulator reaches TrainingMap, starts AirSimGameMode, and creates the native benchmark menu without Unreal Editor. Historical results include cone-free manual mapping laps and a cone-free SLAM Toolbox autonomous lap.
Primary unresolved issues
No current trained behavior-cloning model exists. The current AMZ teach-and-repeat artifact set is incomplete: the active sensor pose graph, cone map and Delaunay centerline are missing even though a closed route is present. Existing general-autonomy and local Delaunay trials did not complete a lap. Multi-vehicle racing and real-kart synchronization are designs, not validated functions.

Current evidence boundary

  • A historical SLAM autonomous result completed one lap in 543.75 s with zero down/out cones; this proves termination, not competitive performance.
  • Two manual mapping runs recorded laps near 456-460 s. The user-reported 44-50 s manual driving target is the performance reference, not the slow recorded runs.
  • Behavior capture metadata reports 2,950 synchronized RGB/depth pairs with no write failures, but the CSV currently contains 2,900 samples; this mismatch must be resolved before training.
  • The latest runtime smoke test verifies menu creation and absence of fatal/missing-package errors; it does not prove every button by automated click-through.

AUTOKART  |  PURPOSE, SCOPE & CLAIMS

Project Purpose & Research Scope

The intended product is an autonomy benchmark tool analogous to a graphics benchmark: choose a sensor and algorithm configuration, execute the same track protocol, and compare completion, lap time, cone contact, speed, stability, and compute behavior under a traceable manifest.

Single Test

Choice familyImplemented or planned optionsMeasured output
SensorsA1M8, A3M1, FSDS 16-layer; HP60C, D415, D435, D455; combined LiDAR + RGB-DTopic availability, rate, range contract, latency/freshness
Localization / SLAMSensor odometry, RGB-D odometry, RTAB-Map, SLAM Toolbox mapping/localizationLoop return, map availability, localization continuity
PlanningReactive Delaunay, persistent mapped centerline, recorded route, behavior cloning, oracle debug baselineCompletion, path validity, interventions
ControlPure Pursuit, Stanley; PID/state-estimator package work remainsLap time, speed, cross-track behavior, cone contact

Multi Test

The planned mode runs three or four vehicles with different profiles, observes them from top/spectator views, and evaluates lap performance, overtaking and collision avoidance. This requires multi-vehicle namespacing, spawn control, per-vehicle bridges, command arbitration and race-state scoring. It is not yet implemented.

Research claim rule: general_autonomy consumes FSDS testing-only track and odometry topics. It is an oracle controller upper bound and debugging tool, not deployable autonomy. Sensor profiles reproduce externally visible data contracts, not full physical optics, sunlight response, projector behavior, USB timing or stereo physics.

Success definition

  1. Reproducible manifest and artifact hashes.
  2. One publisher owns vehicle control.
  3. Safe disabled start and stale-input braking.
  4. Repeated complete laps, not a single anecdotal success.
  5. Zero cone contacts and explicit failure reporting.
  6. Fair comparisons under equal speed and stopping rules.

AUTOKART  |  VIO & VSLAM

Visual Odometry & Mapping

VIO baseline

The vio package launches synchronized RGB-D odometry and an IMU adapter, publishing /localization/vio/odometry. Recorded console evidence showed repeated RTAB-Map odometry updates with roughly 700-800 visual correspondences and approximately 0.10-0.13 s delay.

What this proves: RGB-D feature tracking, synchronized depth and odometry publication operated in the simulator. It is a visual-inertial initialization baseline, not a final tightly coupled estimator.

VSLAM baseline

RTAB-Map receives RGB, depth, calibration, VIO odometry and IMU initialization. Loop-closure views and a 3D cloud were observed. Early 3D-map displays looked like dense planar cells because the depth cloud was being visualized without a useful persistent trajectory/map interpretation.

RGB + registered metric depth + camera_info
                 |
          rgbd_odometry + IMU init
                 |
          RTAB-Map graph / loop closure
                 |
            map -> vio/odom -> fsds/FSCar

Remaining work

  • Quantify drift against evaluation-only ground truth.
  • Run repeated loop closures and record graph corrections.
  • Separate mapping and localization trials.
  • Add a proper fused state estimator and calibrated covariance.
  • Validate the same frame/timestamp contract on the physical RGB-D camera.
Interpretation rule: A visually dense RTAB cloud is not by itself evidence of accurate localization. Map consistency, loop-closure residuals, trajectory error and repeatability must be measured.

AUTOKART  |  AMZ-STYLE LOCAL PLANNING

Reactive Delaunay Autonomy

Implemented algorithm

  1. Filter and cluster LiDAR returns into cone candidates.
  2. Separate left/right boundaries.
  3. Build Bowyer-Watson Delaunay triangulation.
  4. Retain opposite-boundary edges inside valid track-width limits.
  5. Use edge midpoints as centerline gates.
  6. Connect gates sharing triangles and grow alternatives with beam search.
  7. Score heading smoothness, width consistency, spacing, horizon and color ordering.
  8. Publish selected path to the safety-gated controller.
/fsds/lidar/Lidar1
  -> cone_detector
  -> /autonomy/cones/left + /autonomy/cones/right
  -> local_planner
  -> /autonomy/delaunay_midpoints + /autonomy/local_path
  -> pure_pursuit
  -> /fsds/control_command

Visualization contract

VisualizationMeaning
Dark linesRaw Delaunay triangulation.
Pale blueValid cross-track gates.
GreenCandidate centerlines explored by beam search.
Thick redLowest-cost candidate.
Magenta pathSmoothed path consumed by controller.

Historical trial outcome

Three delaunay_phase1 results ended by manual stop or 180 s time limit. Distances were 0-6.36 m; none completed a lap. These files are useful failure evidence but not proof of autonomous operation.

Fallback behavior: If safe Delaunay gates are unavailable, the planner tries paired cones and then conservative single-boundary offset. If no method is safe, it publishes an empty path and the controller brakes.

AUTOKART  |  CONTROL & SAFETY

Teleoperation, Controllers & Motion Safety

Manual control

KeyFunction
EArm/disarm manual control.
W / SThrottle / reverse or deceleration behavior.
A / DSteer left / right.
SpaceEmergency brake.
QStop teleop process.

Controller safety behavior

  • Disabled by default and armed through service/script confirmation.
  • Fresh path and GSS speed required.
  • FSDS GO signal required where configured.
  • Stale/missing input produces full brake.
  • First new cone contact can terminate benchmark.
  • Full-lap event stops and writes result.
  • Concurrent command publishers are rejected.

Static-friction launch assist

launch throttle:       0.55
pulse duration:        0.10 s
release speed:         0.10 m/s
failure timeout:       0.75 s

if speed reached -> normal tracking
if timeout reached -> full brake + disarm; no automatic retry

This bounded kick addresses observed FSDS static resistance without globally changing Unreal friction. It must be tuned from command/GSS recordings.

Safety rule: Never run keyboard teleop and an autonomous controller simultaneously. Exactly one publisher must own /fsds/control_command.

AUTOKART  |  SIMULATION TO REAL KART

Real-Kart Synchronization Plan

Target hardware context

ESP32-S3 vehicle controller; two NEMA 23/TB6600 axes for steering and brake; BLD750/BLDC traction through a 0-5 V PWM-to-voltage converter; steering/brake feedback and chassis sensing.

Autonomy computer / Jetson                         ESP32-S3 VCU
ROS desired steering, throttle, brake  -------->  deterministic actuator loops
ROS heartbeat + mode + sequence        -------->  watchdog / command validation
actual steering/brake/speed/faults     <--------  timestamped telemetry
                                                   |
                         +-------------------------+-------------------+
                         |                         |                   |
                 TB6600 steering            TB6600 brake         BLD750 traction

Required command architecture

  • Simulation and real-kart adapters expose the same high-level command and feedback interfaces.
  • The VCU, not ROS, owns pulse generation, limits, enable polarity, watchdog and emergency stop.
  • Manual RC, autonomous ROS and simulator mirroring require explicit mode arbitration.
  • Physical feedback drives the simulator only in a dedicated hardware-in-the-loop mode; simulated state must never overwrite safety-critical real feedback.
  • Every command carries sequence, timestamp and timeout.

Validation stages

  1. Software-in-the-loop without hardware motion.
  2. VCU bench with disconnected actuators and synthetic feedback.
  3. Hardware-in-the-loop with motors unloaded/lifted.
  4. Manual RC mirrored into simulator.
  5. Autonomy commands observed but not actuated.
  6. Low-speed closed-course autonomous test with independent E-stop.
Safety boundary: Behavior cloning or simulator autonomy must never directly generate step pulses or analog motor voltage. It produces bounded vehicle-level targets; the VCU enforces hardware limits and can always reject or stop them.

AUTOKART  |  CONCLUSION

Conclusion & Immediate Actions

The project has achieved a credible autonomy research platform: the simulator is repository-owned, ROS 2 sensor/TF integration works, several autonomy families share a common test contract, the benchmark UI runs in a standalone package, and historical mapping/autonomous results are preserved. The strongest engineering work is the infrastructure around reproducibility, safety-gated control and algorithm comparison.

The central gap is no longer “can FSDS connect to ROS?” It is “can one non-privileged autonomy profile repeatedly complete the track at useful speed?” The evidence currently says no. The route/SLAM path completed slowly in the past, local Delaunay did not complete, AMZ replay lacks active artifacts, and behavior cloning lacks a trainable multi-run dataset and model.

Next five actions

  1. Fix the behavior dataset sample-count mismatch and improve validator failure reporting.
  2. Generate one clean AMZ map/centerline package from a manual 44-50 s-quality lap.
  3. Run conservative AMZ loaded-map replay with complete RViz evidence.
  4. Establish three cone-free laps, then tune toward a median below 60 s.
  5. Complete packaged UI click-through and add result-history visualization.
What has genuinely been achieved: A configurable FSDS autonomy benchmark foundation with working sensor integration, C++ autonomy components, teach/localize/replay infrastructure, behavior-cloning tooling, safety gates, manifests/results and a normal standalone simulator UI.
What must not yet be claimed: Production autonomy, repeatable sub-60-second laps, validated behavior-cloning control, complete AMZ replay, multi-vehicle racing, or safe real-kart autonomous actuation.

Report basis

Repository inspection on 28 September 2026; Git history through 88e318a6; generated result/map/dataset artifacts; package/runtime validation record; and the project development history. Static code presence is kept separate from simulator-observed behavior and repeatable performance evidence.
